# TTS RTF 与流式输出实测

## 目标

确认 `/v1/audio/speech` 的 4096 字符限制来源，测量 `tts-1`、`tts-1-hd` 的首字节时间和实时因子，并判断当前中台是否适合改为流式音频输出。

## 测试方法

- 使用仓库外服务端环境配置和虚构中文文本调用真实上游。
- 输出格式为 MP3，声音为 `alloy`，语速为 1.0。
- 记录 HTTP 状态、首字节时间、完整响应时间、分块传输信息和音频字节数。
- 使用 `ffprobe` 获取生成音频时长。
- RTF 定义为完整响应耗时除以音频播放时长；RTF 小于 1 表示生成快于实时播放。

## 实测结果

| 模型 | 字符数 | 首字节 | 完整响应 | 音频时长 | RTF | 生成速度 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `tts-1` | 44 | 1.332 秒 | 2.958 秒 | 9.456 秒 | 0.313 | 3.20 倍实时 |
| `tts-1` | 220 | 2.783 秒 | 10.481 秒 | 47.016 秒 | 0.223 | 4.49 倍实时 |
| `tts-1` | 528 | 2.116 秒 | 20.245 秒 | 113.424 秒 | 0.179 | 5.60 倍实时 |
| `tts-1-hd` | 220 | 3.118 秒 | 12.322 秒 | 47.256 秒 | 0.261 | 3.83 倍实时 |

全部成功响应均为 `audio/mpeg`，无 `Content-Length`，使用 `Transfer-Encoding: chunked`；首字节后仍持续传输 1.6-18.1 秒，说明上游确实可以渐进返回原始音频字节。

## 结论

- 4096 字符是 OpenAI 兼容 Speech API 的单次 `input` 上限，不是浏览器限制。
- `tts-1` 和 `tts-1-hd` 不支持 SSE 音频事件流，但支持原始音频字节的分块响应。
- 实测 RTF 全部显著小于 1，且首字节约 1.3-3.1 秒，因此适合实现端到端渐进播放。
- 当前中台尚未流式输出：基础客户端使用普通 `post` 缓冲完整音频，FastAPI 使用普通 `Response`，前端调用 `blob()` 后才开始播放。
- 超过 4096 字符需要按句子边界切分为多个上游请求；是否流式传输与单次输入限制是两个独立问题。

## 兼容性发现

临时探针使用 Python urllib 默认请求签名时，上游 WAF 返回 403/1010；使用标准 OpenAI 请求标识后成功。项目实际 `httpx` SpeechClient 已单独冒烟验证成功，不受该问题影响。

## 建议

1. 后端新增真正的 `StreamingResponse` 路径，使用 `httpx.AsyncClient.stream` 转发 MP3 字节。
2. 首字节发出后不得透明重试；断连和完成状态都必须补齐审计。
3. 前端优先使用 MediaSource 渐进播放，并保留完整 Blob 播放作为兼容回退。
4. 长文本按句子边界拆分，并记录一次业务请求对应的多个真实上游调用。
